## 用户反馈"603173 拉取数据只加载了一半" — 诊断结论（未改代码）

**结论：数据完整，非缺失 bug。603173（福斯达）是 2023-01-30 上市的新股。**

- 603173 日线 854 行完整：2023-01-30（上市首日）~ 2026-08-04，无异常缺口（>5 天均为节假日）。
- 回测区间默认 2020-01-01 起，上市前 3 年无行情 → 曲线/K线只显示 2023 年后半段 → 用户误以为"只加载了一半"。

- **排除的假设**：`stock_zh_a_hist_tx` 的 `get_tx_start_year` 提升 start 的"截断"疑虑不成立——对次新股它返回的就是真实上市首日；腾讯新旧接口（proxy.finance.qq.com / web.ifzq.gtimg.cn 的 newfqkline/fqkline）对次新股同样只保留上市后数据，老股（601113=1595 条）能拿全历史。akshare 内部按年分块 + start 提升逻辑本身 OK。

**顺带发现（值得注意）**：
1. **MySQL 批次/run 时间戳是 UTC**（batch_runner 用 `datetime.now(timezone.utc)`），比北京时间早 8 小时。`backtest_runs.created_at=21:32:47(UTC)` = 北京 05:32:47，与 meta_json `generated_at=05:32:46(+08:00)` 吻合。**看批次时间务必换算**，否则会把"刚跑 12 分钟"误判成"卡了 8 小时"（9b6147a3 批次 8/5 05:22 北京创建，05:34 服务停止，2158 done + 8 running + 53 pending 是**服务被停导致未完成**，不是卡死）。
2. 服务当前已停止（8000 端口无监听、无 python 进程）；数据文件 5:32-5:34 更新是停止前最后一批。
3. 建议（未实施，待用户确认）：回测详情/图表对"数据起点晚于回测起点"的次新股加提示（如"该股 2023-01-30 上市，行情自上市日起"），避免误解；或回测起点自适应。

## 已实施：腾讯源 640 条上限防御——完整性校验 + 自研按年分块循环补拉（用户要求）
- **关键实验（腾讯接口真实行为）**：
  - **新接口** `proxy.finance.qq.com/ifzqgtimg/appstock/app/newfqkline/get`：**忽略 start 日期**，总是返回"end 往前推 640 个交易日"（实测 601113 请求 2020 段返回 2018-05-18 起 640 条、2016 段返回 2014-05-12 起 640 条）。
  - **旧接口** `web.ifzq.gtimg.cn/appstock/app/fqkline/get`：尊重 start/end（实测 2020 段返回 2020-01 起）。
  - akshare 1.18.64 用**新接口** + 按年分块（range_start~range_end 每年一段）→ 多段拼接去重后**正常能拿全**（601113=1595 条），但任一分块失败/未来行为变化会静默丢历史。
  - `get_tx_start_year` 用 weekTrends 接口查**真实最早数据日**（601113→2011-05-09、603325→2024-01-10），不会错误提升（此前"640 条内最早日期"的猜测排除）。
- **tencent_src.py 改动**（防御性加固，正常路径零开销）：
  1. `_fetch_akshare_df`：原 akshare 调用抽出（共享池 + 超时不变）。
  2. `_ensure_tx_complete`：校验 akshare 结果首日 vs 请求起点，**差 >15 天**才继续；再调 `_get_tx_start_date`（weekTrends）判定——akshare 首日 ≈ 腾讯真实最早日 → 次新股数据完整**不补拉**（0.1s 快速判定）；否则判定真缺失 → `_fetch_tx_yearly` 整体重拉。
