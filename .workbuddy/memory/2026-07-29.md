# 2026-07-29 工作日志

## FR-55：快速回测缓存末日容差修复

**问题**：快速回测同一股票，每次提示"本地没有数据需要重新拉取"，即使用户刚回测过、数据已缓存。

**根因**：`backtest.run_symbol` 的 verify 模式调用 `_ensure_verify` → `_covers(meta, beg, end_str)`。快速回测表单的 end 默认填"今天"（如 20260729），但缓存的 meta.end 永远是实际最后交易日（如 20260728），导致 `me >= end` 永远为 False，每次 verify 都抛 DataMissingError。

**修改**（只动快回测 verify 路径，数据生产端不动）：

1. **cache.py** `_covers`：新增 `end_tolerance_days=0` 参数。当 `me < end` 且 tolerance>0 时，容忍末日落后最多 N 天。
2. **provider.py** `_ensure_verify`：使用 `VERIFY_END_TOLERANCE_DAYS = 7` 调用 `_covers`（含旧格式兼容回退分支）。

其他调用方（`load()`）默认 tolerance=0，行为不变。

## FR-55 补充：新股首日容差（2026-07-31）

**问题**：末日容差修复后，301531（2026年5月上市新股）仍然每次回测都要重新拉取。

**根因**：`_covers` 的 `mb <= beg` 检查对新股永远失败（缓存首日=20260511 > GENESIS=20200101），end 容差根本没机会执行就返回 False。update 模式拉取到的数据首日也还是 20260511（IPO 日），形成死循环。

**修改**：`provider.py` 新增 `_end_within_tolerance` 静态方法 + `_ensure_verify` 中增加新股 fallback：
- `_covers` 失败后，若 meta 存在（说明有缓存），回退为仅检查末日容差
- 逻辑：数据源本来就没有上市前的数据，只要末日足够新，缓存即视为可用
- 旧格式兼容回退分支也同步增加 fallback
