# 2026-08-13

## 分析查询「策略统计分析」一直卡在"统计计算中" — 根因与修复

现象：/analysis 页右侧"策略统计分析"面板长期显示"统计计算中…"（实际是 N 秒甚至几分钟不返回）。

根因（两层）：
1. **前端翻页放大**：`web.py` 的 `loadStats()` 用 `size=500` 翻页拉 `/api/rank` 全量。默认策略(周线MACD+日线KDJ)有 2216 条 run → 翻 5 页；每页 `rank_runs` 都全量重算 → 5×7.3s≈34s（撞 200 页上限时更可达 22 分钟）。
2. **后端单次慢**：`repository.rank_runs` 每次都把该策略全部 run `all()` 进内存 + join summary + 对 `trades` 做 2 次聚合（原用 `Trade.run_id.in_(2256个id)` 大 IN 列表，约 2.5s）+ ORM 物化。单次即 ~7.3s。

修复：
- `web.py`：`STATS_PAGE_SIZE` 500 → 100000，统计改为**一次拉全量**（后端 size 上限同步放开到 100000），翻页循环第 1 页即 `all.length>=total` 结束。
- `repository.py`：两处 trades 聚合由 `IN(run_ids)` 大列表改为 `JOIN backtest_runs WHERE strategy_name+params_hash`（等价、更快、避免上千 id 展开）。
- 已重启服务（kill PID 18584 + `venv python -m strategylab`）使改动生效。

验证：
- `rank_runs` 单次 7.33s → 3.10s；`profit_factor` 与原 JOIN 查询逐条核对一致（数据无影响）。
- `/api/rank?size=100000` 一次返回 2216 条 / 3.1s；统计面板现在 ~3s 出结果。
- 附带好处：rank 表分页（size=50）也由 7.33s → 3.6s。

注：`summary` 表无 `profit_factor` 字段（盈亏比只能从 `trades` 聚合），故统计单次仍有 ~3s 固有成本。若要瞬时，需 (a) 加服务端专用 stats 聚合接口，或 (b) 回测落库时把 `profit_factor` 预存进 `summary`/`backtest_runs`。可作为后续优化。
