## 3. 诊断"更新数据源后回测仍去新浪联网"（当前任务）
- 根因：回测 `fetch_end=max(end, today)` → `required_end=今天(20260728)`；verify 用 `cache._covers` 要求缓存覆盖到今天。
- 实测：`.env`=akshare；akshare 日线 meta 末日多为 0719/0720/0721（2211个文件），周线多为 0724/0719（2210个）→ 均 < 0728。
- 结论：缓存末日 < 今天 → `_covers` 返 False → DataMissingError → 降级 `mode=update` 经 akshare(新浪) 联网补最近几天。**非 bug，是 verify 必须覆盖到今天的设计行为**，也不是前缀错配。

## 5. 统一日期起点 + 修复 verify 过度拉取

### 5a. 统一日期起点：更新数据源与回测都从 2020-01-01 开始
- **问题**："更新数据源"用 `20220706`(日)/`20211210`(周) 作 genesis，而"回测"用 `2020-01-01`，两者不统一。
- **修改**：将所有 genesis/beg 默认值 + 前端日期选择器统一为 `2020-01-01`。
- **涉及文件**：provider.py, data_feed.py, batch_runner.py, web.py, cli.py
- `daily_lmt` 从 1500→2500（2020 年起数据量更大）

### 5b. 修复 verify 过度拉取（重要）
- **问题**：`required_end = max(end, today)` 导致 verify 要求缓存必须覆盖到**今天**（而非仅覆盖回测区间），缓存末日差几天就触发重拉。
- **修复**：verify 用 `end_str`（回测实际结束日）做 `required_end`；update 模式仍用 `fetch_end_str = max(end, today)` 确保补数据时拉满。
- **效果**：只要本地缓存覆盖了回测区间 `[daily_beg, end]`，就不会触发联网取数；只有回测 end 超出缓存范围时才补数据。

### 5c. 回测 warmup 起点钳位 + web 多股回测多线程
- **问题**：`daily_beg = start - 1年` 在 start=2020-01-01 时前推到 2019-01-01，而 genesis=20200101，导致 verify 总是失败。
- **修复**：`daily_beg = max(GENESIS, start-1yr)` / `weekly_beg = max(GENESIS, start-1.5yr)`，钳住下限不早于 genesis。
- **web 多股回测多线程**：`run_backtest()` 原本串行 for 循环 → `ThreadPoolExecutor(max_workers=min(n, 4))`。
- 每个 worker 内嵌 try/except，单股失败不中断整批；全部失败时抛出 RuntimeError。
- 并发度：web 默认 4（`STRATEGALAB_WEB_WORKERS`），批次默认 8（`STRATEGALAB_BATCH_WORKERS`）。
- 用户反馈回测中途服务崩溃，日志太旧无法定位。已加固：降低默认并发、添加逐股异常兜底、全面失败兜底报错。待用户重启服务后观察。
