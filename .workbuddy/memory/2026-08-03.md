## 快速回测成交量缺失 → 根因 + 修复（重要）
- **现象**：用户首页快速回测，combo_chart 成交量显示缺失。
- **根因（两层）**：
  1. **历史数据缺口**：08-02 21:39 前用旧 akshare 适配器（未抓 vol）拉的全市场缓存 vol 全空/缺列——统计：2216 个 akshare 日线缓存中 2181 个 vol 空（98.4%），仅 35 个（21:39 后拉的）正常。代码全链路实测无 bug（适配器→merge→写盘→combo_chart 均验证 vol 正常）。
  2. **逻辑缺陷**：`ensure_data` 的 update 模式增量窗口只看 meta.last 是否最新——缓存 last 落后时只拉 last+1 之后（可能周末空段），**历史段 vol 永不补齐**；用户点「更新数据源」也补不上。
- **修复**（provider.py + cache.py，最小改动）：
  - `cache.py` 新增 `KlineCache.has_volume_data(csv_path)`：轻量 vol 健康检查（nrows=5 抽查，非全文件扫描）。
  - `provider.py` update 模式：`daily_vol_missing`/`weekly_vol_missing` 判定 vol 缺失 → 强制 `beg_calc=daily_beg`（genesis 全量重拉），merge 补齐历史段；vol 正常 → 原增量逻辑不变；legacy-skip 加 `not vol_missing` 条件；锁内沿用检查结果。
  - verify 模式（快速回测）完全不改（仍只校验覆盖）。
- **验证**（主理人亲自）：
  - vol 缺失缓存 → update 全量重拉 → vol 4/4 补齐 ✓
  - vol 正常缓存 → 纯增量 last+1，不重拉历史 ✓
  - has_volume_data 五种边界全对 ✓
  - 修复代码前已端到端验证：重拉后 combo_chart.ohlc 2081/2081 带 volume（前端能画成交量）。
- **测试修复**（tests/test_data_feed_cache.py）：`_fake_klines_df()` 补 vol 列 + 首日改 2019（避免"往前补"恒重拉）+ 末日=today（避免"落后"恒增量）；`test_atomic_write_no_tmp_leftover` 的 `meta["version"]` 断言 2→3（既有版本号失配）。3 passed。K线+数据缓存合计 13 passed。
- **教训**：① 测试 fake 数据必须满足增量语义的两个前提（first < default_beg 且 last == today），否则幂等断言必挂；② SymbolSpec 是 dataclass，构造用关键字（symbol/secid/prefix），位置参数易把 prefix 传错导致文件名不符；③ 排查数据缺失问题先量化影响面（统计全市场 vol 空置率），能快速定位"历史数据缺口"而非代码 bug。
- **用户决策**：按需修复（用户自己会重拉数据）+ 不加 vol 缺失检测代码增强。修复后用户只需点首页「更新数据源」（POST /api/data/update，update 模式）即可批量补齐 vol。

## 详情页"一直加载"卡死 → 根因 + 修复（重要）
- **现象**：分析查询点行进详情（/history?run_id=）快速回测过的 run 一直转圈加载；旧回测 run 正常。
- **根因**：`repository.get_run` 和 `list_runs_by_ids` 对 equity/price/trades **三个一对多关系同时用 `joinedload`** → SQLAlchemy 生成 **JOIN 笛卡尔积**（equity × price × trades ≈ 4000 万行）→ MySQL 查询挂起。旧 run 无 price_points（JOIN 退化小）所以正常；快速回测 run 有 ~1594 个 price 点 → 笛卡尔积爆炸。
- **修复**：repository.py 两处 8 个 `joinedload` → `selectinload`（一对多关系标准做法，分开发 SQL 走 run_id 索引，不产生笛卡尔积）。`joinedload(summary)`（一对一）保留。
- **验证**（主理人亲自）：get_run 0.05s / list_runs_by_ids 0.1s（修复前 >60s 卡死）；build_compare_from_runs 0.05s，combo_chart 正常生成（ohlc 1594 + points 466）；13 passed。
- **教训**：① **多个一对多关系 joinedload = 笛卡尔积炸弹**，凡出现"单条查询卡死、列表正常"优先怀疑；② 排查顺序：先量化（表行数/每 run 点数）→ 直查 SQL 计时 + EXPLAIN（排除索引问题）→ 定位 ORM 加载策略；③ equity_points 全表 827 万行（batch 回测积累），单 run 实际 400-500 点，别被全表规模误导。

## 盈亏比（Profit Factor）列 → 分析列表 + 详情页（FR-44）
- 需求：分析查询排名列表 + 股票详情仪表盘显示"盈亏比"。

## 回测报错 [Errno 22] + 换策略没反应 → 根因（重要）
- **现象**：用户"回测报错"（控制台 RuntimeError: 600216.SH: [Errno 22] Invalid argument）+ "跑完一个策略再换策略就没反应"。
- **根因**：**8000 端口同时有多个服务实例在监听**（排查时 netstat 显示 26484 + 4532 两个 LISTENING；更早还有残留）。多实例并发跑回测 → 同时读写同一批缓存 CSV（data/*_akshare_*.csv）→ Windows 下 `cache._atomic_write_csv` 的 `os.replace` 报 `[Errno 22] Invalid argument`（目标文件被另一进程占用）。这也是"换策略没反应"的真相：不是前端卡，是后端 500。
- **排查关键**：① 服务日志此前只进启动窗口（`> log 2>&1` 后台组合在 bash 里失效），看不到 traceback → 用 Python FileHandler 启动器 `_start_with_log.py` 让日志落盘；② HTTP 500 响应体里有真实错误（`回测出错` 页）；③ 直调 run_backtest 成功、HTTP 500 → 锁定是**进程环境差异** → netstat 发现多实例。
- **修复**：杀掉所有残留 python 进程（PowerShell Stop-Process），只留一个实例。验证：同策略连跑 3 次 + 换 turtle 全 HTTP 200（0.4s），不再报错。
- **教训**：① 排查服务端问题先看 `netstat -ano | grep LISTENING` 是否多实例——多实例抢占文件是最隐蔽的"间歇性 Errno 22"来源；② restart.bat/restart.sh 的 taskkill 在 Git Bash 里参数转义有问题（`//F`），停服务用 PowerShell Stop-Process 更可靠；③ 服务日志落盘用 FileHandler 启动器，别依赖 shell 重定向。
- **遗留**：`server_console.log` 现为服务日志（FileHandler 写入，mode=w），可保留供后续排查；`_start_with_log.py` 已删。
- 教训：盈亏比这类"可由已有数据推导的指标"，优先读取时动态算（零迁移、历史全生效），别急着加列——除非数据量巨大需预聚合。
