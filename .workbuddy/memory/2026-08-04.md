## 服务重启踩坑（重要）
- **Bash `run_in_background` 启动的常驻服务会被后台任务系统回收**：任务运行 ~58s 后标记 failed 并终止进程树（服务监听消失）。**不能用 run_in_background 跑服务**。
- **正确姿势**：Python `subprocess.Popen(creationflags=DETACHED_PROCESS | CREATE_NEW_PROCESS_GROUP | CREATE_NO_WINDOW, close_fds=True)` 启动，进程独立于会话存活（实测 PID 9900 稳定 HTTP 200）。
- 沙箱下 `nohup`/`timeout`（GNU）不存在（Windows 命令冲突）、`cmd //c start` 起不来（沙箱禁窗口）、PowerShell `Start-Process` 被拒（exit -1）。

## 服务重启踩坑 2（更准确结论）
- **沙箱 Job Object：本会话启动的任何进程（含 DETACHED_PROCESS subprocess）都会在会话 turn 结束时被 kill-on-close 回收**。实测 9900（detached）在 turn 结束后消失，服务日志无崩溃痕迹。
- **结论：WorkBuddy 沙箱内无法代为常驻服务，重启服务必须由用户在桌面环境运行 `restart.bat`（或终端 `python -m strategylab`）**。

## 晚间再次卡死：requests 无超时导致池死锁（已治本修复）
- **现象**：用户反馈日志卡在 600984。查 MySQL：data 批次 19556c2a + backtest 批次 f2c0e240 **各有 8 个 running 项从 14:13 卡到 22:20（8 小时）**，卡住的是 600955-600984 连续段 + 300862（同一秒），done 停滞、pending 470+。
- **根因（重要教训）**：新浪接口限流挂起时，**requests.get 无 timeout → TCP 挂起永不返回**。上一轮共享线程池方案只解决"线程爆炸"，没解决挂起：`_fut.result(timeout=15)` 只是调用方放弃等待，**底层请求仍占着池槽** → 4 个池槽被挂起任务占死 → 队列 470+ 无限排队 → 死锁。
- **治本修复**：`akshare_src.py` 加 `_ensure_requests_timeout()` 幂等补丁——monkey-patch `requests.get/post` 注入默认 `timeout=(8, 15)`（connect 8s / read 15s），`_import_akshare()` 时调用。挂起请求 ≤15s 自行抛超时结束、线程释放。**已验证**：黑洞地址 10.255.255.1 8.0s 抛 ConnectTimeout。
- **部署**：已 kill 卡死服务（PID 2220），需用户 restart.bat 重启；重启会把两个卡死批次标 interrupted，用户重提交（重新全市场更新 + 回测）。
- **核心教训**：给第三方库（akshare 内部 requests 不传 timeout）做超时保护，`Future.result(timeout)`/`join(timeout)` 都只是"调用方放弃等待"，**必须让底层网络请求真正超时**（注入 requests timeout 或 socket 级），否则线程/池槽永远被挂起占用 → 死锁。此教训已远超"线程泄漏"，是批量抓取类系统的通用坑。

## 设计修正：缓存优先、同股同源（用户质疑"为什么缓存按源分"）
- **用户诉求**：只在乎数据不在乎来源，反对一只股票多份缓存文件、换源重建。
- **解释**：缓存按源分文件是**数据一致性必要**（不同源前复权价格不同，混源 merge 会跳变）；但同股应尽量单文件。
- **最终方案**（cache.py + provider.py + batch_runner.py）：
  - `cache.find_existing_source(out_dir, prefix, active_sources)`：找该标的已有缓存文件的源。
  - `provider.ensure_data` 生效源 = **已有缓存源优先**；无缓存（新股）才按 active_sources 轮询。batch_runner 预判定同步。
  - 效果：**已有缓存的股票永不换源不重建**（2218 只 akshare 缓存全部保持 akshare）；**新股首建缓存时轮询分散到 3 源**（建缓存是大请求，恰好分散压力）；增量更新（小请求）集中在新浪但量小无害。
- **验证**：2218 只已有 akshare 缓存 → 生效源 100% akshare；9 只新股 → 5/2/2 分散；000001（轮询主源 eastmoney）→ 缓存优先 akshare。
- **架构要点**：请求分散的正确时机是"全量建缓存"（大请求），而非"增量更新"（小请求）。轮询池 + 缓存优先 = 既分散大请求又保持单文件一致性。

## 设计定稿：换源全量覆盖 + 缓存收敛（用户："回测会重新计算，不在乎各源价格不一致"）
- **用户论点**：各源前复权价不一致没关系，每次回测基于当前数据重新计算即可。
- **认同 + 前提**：论点成立的前提是**单份缓存文件内部同源**——混源文件在换源拼接点出现假跳空，指标算错，重新计算救不了。故不追求"文件跨源等价"，只保证"文件内单源"。
- **最终机制**（provider.py）：
  - `_try_fetch` 改为返回 `(df, source_name)`（实际取数成功的源）。
  - update 分支：`source_name == effective`（同源）→ 增量 `merge`；`!=`（容灾切换）→ **`save` 全量覆盖写新源文件**（不 merge 旧数据，杜绝混源）+ **`_prune_other_sources` 收敛删除该股其他活跃源缓存**（同股磁盘仅 1 份文件）。
  - 收敛后 `find_existing_source` 返回新源 → 后续增量稳定用新源，闭环。
- **验证**：mock 造 akshare 旧缓存 → 模拟 eastmoney 切换 → 文件从 `*_akshare_daily.*` 收敛为 `*_eastmoney_daily.*`，find_existing_source=eastmoney ✓。
- **最终用户视图**：同股始终 1 份缓存 + 文件内单源 + 新股轮询分散 + 三源互为容灾。无需迁移磁盘存量（改名会撞 legacy `*_daily.csv`）。
