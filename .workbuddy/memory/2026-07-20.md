## QA 方法论教训（重要，避免未来误判）

## 东财 Referer 中文导致 latin-1 崩溃（2026-07-20 深夜，接续切东财后）
- 用户报告切东财后"跑了一个直接失败"。排查：服务(PID 21748)正常、MySQL(3306)可达。**真实批次库在 MySQL**（`DATABASE_URL=mysql+pymysql://root:root@localhost:3306/strategylab`，在 `.env`），不是本地那个 0 字节 `strategy_lab.db`（误导项）。
- 根因：`src/strategylab/engine/datasource/base.py` 第51行 `_DEFAULT_REFERERS` 池含中文 `"https://www.baidu.com/s?wd=股票行情"`；`random_headers()` 随机选 Referer 作 HTTP 头，HTTP 头须 latin-1 编码，中文无法编码 → `urllib` 抛 `UnicodeEncodeError: 'latin-1' codec can't encode characters in position 27-30`。**间歇性(1/6 概率)**，所以部分股票成功部分失败。新浪源走 akshare/tushare 第三方库不套此伪装头，故从不暴露；切东财才触发。
- 修复（工程师寇豆码，仅 `base.py`）：删掉中文 baidu referer（剩5条纯ASCII eastmoney系）；新增 `_ascii_safe()` 对 header 值做 latin-1 安全化（非 ASCII 百分号编码），`random_headers()` 的 UA/Referer 均经其包裹（防御性，未来加中文也不崩）；顶部补 `from urllib.parse import quote`。
- 验证：重启 8000（PID 22968）后，用之前失败的那只 `600839.SH` 跑 `curl -F scope_type=pool symbols=600839.SH /api/data/update` → `status=done, done=1, failed=0` ✅（此前该批 `44b08811` 正是此 latin-1 错误）。
- 经验教训：HTTP 请求头（User-Agent/Referer）必须 ASCII/latin-1 安全；凡用 `urllib` 自发包头的伪装池，值里绝不能含中文，或统一经 `_ascii_safe` 类处理。
