## 全市场预热 - 数据更新行为分析（为 3.0 需求铺垫）
- 用户提出 3.0 新版本需求，先问现有"全市场预热"更新数据源时是全量重拉还是增量追加新日期。
- 调用链：/api/batch/warmup-all (web.py:1198) → batch_runner.submit_batch (42) → _run_one (154, end=datetime.date.today()) → run_symbol → backtest.ensure_data(daily_end=today) (backtest.py:43-51) → datasource/provider.ensure_data → cache._covers / _try_fetch / save。
- 关键结论：
  1. submit_batch 的"命中复用" find_existing_runs 命中条件 = strategy_name + params_hash + symbol + data_source，**不比对日期区间**（repository.py:320-329，注释明确写"end 不严格匹配"）。同策略重跑 → 所有标的 status=skipped → run_symbol/ensure_data 根本不调用 → 数据冻结在首次预热，完全不更新。
  2. 换策略/首次跑 → ensure_data 因 daily_end=today 永远 > 缓存 meta.end → _covers 必 False → 全量重拉 [start-1y, today]；cache.save 用 os.replace 整文件覆盖（cache.py:242），无 merge/append。
  3. 不存在"仅追加新日期"的增量更新逻辑。数据更新与回测执行强耦合，无独立 refresh 命令。
- 3.0 若要真增量更新：ensure_data 需改为 fetch [last_cached_date+1, today]，save 改为 merge/append；且 submit_batch 命中键需把日期区间纳入，否则同策略重跑会跳过数据刷新。

## QA 方法论教训（重要，避免未来误判）
- QA 第 2 轮做"最小复现"时，是在**工程师已修复的代码**上验证，于是误判"两处源码 bug 都是假阳性、无需修复"，并建议关闭修复任务。实际两处都是真实 bug、修复必要。
- **铁律**：验证"原代码是否有 bug"时，必须确认被测代码是**原始版本**；若在已修复版本上复现，必然得不出原 bug。归因存疑时，用项目代码做最小独立复现（如本例 `_normalize_dates` 输出类型 + 字符串调 `.strftime` 直接 CRASH）一锤定音，不要仅凭 agent 文字结论下判断。主理人应亲自读代码/跑最小复现核实关键归因。

## Bug 修复：板块缓存永不失效 → "全市场"展开为空（2026-07-20 晚）
- 现象：用户选「全市场」+「更新数据源」提示"没有可更新的标的"（web.py:1276 的 `items` 为空分支）。用户数据已跑到 2026-07-17，今天 7/20 本应可增量更新。
- 诊断（主理人亲自跑诊断脚本 + 读源码）：`data/sector_stocks.json` 正常（31 板块/1301 只）；全新进程 `_expand_all_market()` 返回 1301，样本 `sz000002` 的 meta `last=20260717` → 增量窗口算得 `20260718`（非"已最新"），增量逻辑本身无 bug。
- 根因：`repository.py` 的 `_SECTOR_STOCKS_CACHE` / `_SECTORS_CACHE` 全局缓存**首次调用后永久缓存、永不过期**；服务在 `sector_stocks.json`（7/19 13:55 生成）之前启动并首次触达缓存时文件不存在 → 缓存成 `{}` → 之后永远返回空 → 全市场展开为空。
- 修复（工程师寇豆码，最小变更 `repository.py`）：两个缓存函数改为按文件 mtime 失效（缓存形状变 `tuple[mtime, data]`，每次比对 `p.stat().st_mtime`，不一致即重读）。文件后生成/更新都能自愈。
- 验证（QA严过关）：新增 `tests/test_sector_cache_invalidation.py` 3 例全过（陈旧空缓存自愈 / 文件更新重读 / 全市场展开不受陈旧缓存影响），`3 passed`。
- 临时 workaround：重启服务即可（进程干净后重读已存在的 sector_stocks.json）。根治已落代码，无需重启。
- 教训：长生命周期服务里"首次调用永久缓存外部文件"是隐患，外部文件可能晚于进程启动才生成/更新；此类缓存须带失效（mtime/版本/ttl）。

## Bug 修复：HTTP 协议层 multipart vs urlencoded 不匹配（2026-07-20 深夜，接续上一 bug）
- 现象（与上一 bug 同一报错，但重启后仍复现）：用户执行全市场更新数据源仍提示"没有可更新的标的"。
- **真正根因（与上一轮"板块缓存失效"是不同问题；缓存修复本身正确，但非本次症状根因）**：前端 `web.py:662 buildScopeForm()` 返回 `FormData()`，经 `fetch(...,{method:'POST',body:fd})` 发送 **multipart/form-data**；后端 `_api_data_update`(1246)/`_api_submit_batch`(1157)/`_handle_compare`(1385)/`_handle_run`(1361)/`_api_warmup_all`(1215) 用 `urllib.parse.parse_qs(raw)` 只认 `application/x-www-form-urlencoded` → `scope_type` 永远读不到 → 落默认 "sector"+空值 → items 空 → 报错。

- 修复（工程师寇豆码，最小变更，仅 `src/strategylab/web.py`）：新增 `_parse_post_body`（兼容 urlencoded/multipart，返回结构同 parse_qs 的 `dict[str,list[str]]`）+ `_parse_multipart`（**手写最小解析，未用 cgi**——Python 3.13+ 已移除 cgi 模块）。替换全部 5 处 `parse_qs(raw)` 调用点；保留 `_handle_compare` 的 JSON 分支。未动前端、未动 `repository.py` 缓存修复。
