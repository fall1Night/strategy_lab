## 二、证据链

### 1. 线程池泄漏（今天批次卡死的直接原因）

`src/strategylab/engine/datasource/akshare_src.py` 的 `_raw_fetch_kline`：

```python
_ex = _cf.ThreadPoolExecutor(max_workers=1)      # 每次取数新建线程池
try:
    _fut = _ex.submit(ak.stock_zh_a_daily, ...)
    df_raw = _fut.result(timeout=self.config.network_timeout)  # 15s 超时
finally:
    _ex.shutdown(wait=False)                     # 不等待 → 工作线程泄漏
```

- 新浪接口无内置超时，15s 后抛错但**底层工作线程仍挂起在网络请求上**，`shutdown(wait=False)` 不回收 → 每次超时泄漏 1 个线程。
- 1301 只 × 日/周 2 周期 ≈ 2600 次取数，新浪接口慢时大量超时 → 线程数耗尽。
- **今天批次（c9e03b37，10:55 提交）失败原因全部是**：
  `RuntimeError: cannot schedule new future`（CPython 无法创建新线程）。
- 状态分布：done=17 / failed=12 / running=8 / **pending=1264** → 批次跑 8 小时无法完成。

### 2. vol 缺失 → 强制全量（8/3 提交 8a097d5 引入）

`provider.py` update 分支新增逻辑：缓存 CSV 无 vol → `[vol修复] 强制全量重拉`。

- **902 只旧缓存（7/18-19 创建）CSV 连 vol 列都没有**（仅 `date,open,high,low,close` 4 列），last 全部停在 20260717。
- `KlineCache.has_volume_data()` 抽查**头部**前 5 行——增量 merge 后头部（2019 年）仍无 vol → 永远判定缺失 → 每次更新都触发全量，且永远无法"自愈"。

### 3. 缓存首日 > genesis → 每次全量

`_incremental_window`：`first > default_beg(20200101)` → 返回 `20200101` 全量起点。

- 全市场 2218 只缓存中 **230 只 beg > 20200101**（次新股 + 历史遗留如 000001=20220104、000029=20201109）。
- 实测模拟：605198 / 301498 / 000001 / 000029 今天窗口均判定为 `FULL`。
- 000001 昨天 21:29 更新后 beg 仍是 20220104 → 全量拉取从未成功写盘 → 今天继续全量。

### 4. 902 只旧缓存不在更新范围

`_expand_all_market()` = **31 个板块成分股去重 = 1301 只**。7/18-19 创建的 902 只旧缓存不在该列表 → all_market 更新永远不覆盖它们 → 数据永久停在 7/17、vol 永远缺失。

### 5. 昨天批次实际失败

MySQL `batches`（8/3 14:24 `2d33e9a4`，1301 只）：skipped=1083 / done=107 / **failed=99** / status=**interrupted**（23:19 服务重启中断）。
99 只失败原因：`[WinError 5] 拒绝访问: tmp → xxx_akshare_weekly.csv`（atomic write `os.replace` 冲突/杀软占用）。

## 三、为什么"昨天更新过，今天还要全量"？

1. **今天批次 skipped=0 是正常的**：昨天成功的 1286 只 last=8/3 < 今天 8/4 → 今天必须补 8/4 一天（这正是用户期望的"只更新今天"）。
2. **但执行过程崩了**：线程池泄漏 → 大量 `cannot schedule new future` → 只有 17 只真正增量成功（000592 等 last→8/4），1264 只 pending 卡死。
3. **部分股票确实全量**：beg>genesis 的次新股（每次全量）+ vol 缺失股票（强制全量），全量拉取进一步加剧线程/限流压力，日志刷屏"全量"。

## 四、修复方案（按优先级）

### P0-1 线程池泄漏（治本，必须）
`akshare_src.py`：改为**模块级共享线程池**（进程内复用），或一次性 `threading.Thread` + `join(timeout)`（join 后线程对象可回收）。
- 目标：杜绝 `cannot schedule new future`，1301 只增量批次应 10 分钟内完成。

### P0-2 vol 全量误判（体验，必须）
`KlineCache.has_volume_data()` 抽查**尾部**（最近 5 行）而非头部：
- 增量 merge 后尾部必有 vol → 不再判定缺失 → 902 只变增量（每只 1-2 行）。
- 历史段 vol 缺失对回测容错（backtest 已按 None 占位），仅副图成交量不完整。
- 如需补全历史段 vol，另做一次**错峰分批全量**任务。

### P1 更新范围（902 只永不更新）
`_expand_all_market()` 并入"磁盘已有缓存标的"（`data/*_akshare_daily.csv` 并集），或提供「按缓存更新」入口。

### P2 atomic 写盘重试
`cache.py` 的 `os.replace` 加 3 次重试 + 短退避，缓解 `WinError 5`。

### P3 日志可读性
打印区分 `[全量拉取]` / `[增量拉取]`，让"全量"一目了然。
